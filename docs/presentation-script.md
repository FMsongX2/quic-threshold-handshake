# 발표 대본

빅데이터처리 term project 발표에 쓰는 대본이다. 발표 시간 10분에 맞추었고, 절마다 슬라이드에 넣을 내용과 말할 문장을 함께 적었다. 수치의 근거는 [results-summary.md](results-summary.md)와 [논문 초안](../paper/paper.md)에 있다.

## 읽는 법

- "슬라이드"는 그 절의 화면에 넣을 내용이다. 그림 파일은 `paper/figures/`에 PNG와 PDF로 있다.
- "대본"은 그대로 읽을 수 있게 쓴 문장이다. 전체가 공백을 빼고 약 2,900자이며, 분당 300자 속도로 10분에 조금 못 미친다. "ms"는 "밀리초"로 읽는다.
- "조건"은 대본의 수치가 나온 측정 조건이다. 슬라이드 각주와 질문 답변에 쓴다.
- 시간이 모자라면 "(생략 가능)"으로 표시한 문장부터 뺀다. 모두 빼면 약 1분이 줄어든다.

## 용어

| 말 | 뜻 |
| --- | --- |
| threshold signature (t, n) | 키를 n대에 나누어 두고 t대가 협력해야 서명이 만들어지는 방식 |
| signer | 키 조각을 가진 서버 |
| 서명 지연 | QUIC 서버가 서명을 요청한 때부터 서명을 받을 때까지의 시간(문서의 D_sign) |
| handshake 시간 | client가 연결을 시작한 때부터 handshake가 끝날 때까지의 시간(문서의 T_hs) |
| p99 | 100번 가운데 가장 느린 한 번에 해당하는 지연. 꼬리 지연의 지표다. |
| 선택 정책 | 서명할 때 어느 signer에 요청할지 정하는 규칙 |
| hedge | t대보다 많은 signer에 요청을 함께 보내고 먼저 완성되는 서명을 쓰는 정책 |

## 1. 무엇을 했는가 (0:40)

슬라이드: 제목, 한 문장 요약, 구성도(`paper/figures/system.png`).

대본:

> 저희 팀은 QUIC 서버의 인증서 개인키를 여러 서버에 나누어 보관하는 구성을 직접 만들고, 이때 연결 수립이 얼마나 느려지는지 측정했습니다.
>
> 키를 나누는 데에는 threshold signature를 썼습니다. 서버 n대 가운데 t대가 협력해야 서명이 만들어지는 방식입니다.
>
> QUIC 서버 구현체 4종과 서명 방식 3종으로 측정했고, 키 조각을 가진 서버를 어디에 두고 어느 서버에 요청할지를 바꿔 가며 지연이 가장 낮은 구성을 찾았습니다.

## 2. 왜 했는가 (1:00)

슬라이드: 세 칸. 문제(서버 한 대 침해 = 키 유출), 해법(threshold signature, t대를 침해해야 함), 대가(handshake 도중의 왕복).

대본:

> 웹 서버는 연결을 맺을 때마다 인증서 개인키로 서명해서 자신이 진짜 서버임을 증명합니다. 그래서 개인키는 연결을 받는 모든 서버에 있어야 하고, 그중 한 대만 침해되어도 키가 유출됩니다.
>
> (생략 가능) 서버가 여러 지역에 흩어져 있는 서비스일수록 이 위험이 커집니다.
>
> threshold signature를 쓰면 완전한 키를 가진 서버가 없어지고, 공격자는 t대를 침해해야 키를 얻습니다.
>
> 대신 연결을 맺는 도중에 키 조각을 가진 서버들과 메시지를 주고받아야 하므로 지연이 생깁니다. 이 지연을 QUIC 구현체별로 측정한 연구는 저희가 조사한 범위에서 찾지 못했습니다. 그래서 얼마나 느려지는지, 어떻게 줄일 수 있는지를 직접 재 보기로 했습니다.

조건: TCP 위의 TLS에서 threshold ECDSA의 응답 시간을 잰 연구(Kolegov 등)와, 서버가 인증서를 기다리는 지연을 client 구현체별로 잰 연구(Mücke 등)는 있다. "처음 측정했다"고 말하지 않는다.

## 3. QUIC (0:45)

슬라이드: QUIC 한 줄 소개(UDP 위, HTTP/3, 왕복 한 번의 handshake), handshake 그림에서 서버가 서명하는 위치 표시.

대본:

> QUIC은 HTTP/3가 쓰는 전송 프로토콜입니다. UDP 위에서 동작하고, 연결 수립과 TLS 1.3의 암호화 협상을 하나로 묶어 왕복 한 번에 연결을 맺습니다. 이 과정을 handshake라고 합니다.
>
> handshake 도중에 서버는 인증서 개인키로 서명을 한 번 만들어 보냅니다. 저희가 threshold signature로 바꾼 부분이 이 서명입니다.
>
> (생략 가능) QUIC은 패킷 손실을 timer로 복구하므로, 서명이 늦어질 때 timer와 맞물려 지연이 더 커지는지도 확인 대상이었습니다.

## 4. 최적화하려는 것 (1:10)

슬라이드: 최적화 문제를 표 하나로.

| 항목 | 내용 |
| --- | --- |
| 목표 | 서명 지연과 handshake 시간의 p99를 낮춘다 |
| 제약 | 한 지역이 침해되어도 키가 안전하다. 한 지역이 멈춰도 서명할 수 있다. |
| 바꿀 수 있는 것 | 지역별 signer 수(배치), 협력 대수 t, 선택 정책 |
| 비용 | signer의 계산량 |

대본:

> 최적화하려는 것은 handshake 지연, 그중에서도 꼬리 지연입니다. 평균이 아니라, 100번 가운데 가장 느린 한 번에 해당하는 p99를 목표로 삼았습니다.
>
> 제약은 보안입니다. 키 조각을 가진 서버, 이하 signer 5대를 3개 지역에 나누어 둘 때, 한 지역이 통째로 침해되어도 키가 안전해야 하고 한 지역이 통째로 멈춰도 서명할 수 있어야 합니다.
>
> 바꿀 수 있는 것은 세 가지입니다. signer를 지역마다 몇 대씩 둘지, 몇 대가 협력해야 하는지를 뜻하는 t, 그리고 서명할 때 어느 signer에 요청할지를 정하는 선택 정책입니다.
>
> 여기에 trade-off가 있습니다. 여유 signer에도 요청을 함께 보내면 느린 응답을 기다리지 않아도 되지만 계산량이 늘어납니다. 분산 시스템에서 hedged request라고 부르는 기법이고, 저희는 이 기법의 효과와 비용을 함께 측정했습니다.

## 5. 실험 설계 (1:05)

슬라이드: 구성도(`paper/figures/system.png`) 옆에 변인과 지표.

| 구분 | 내용 |
| --- | --- |
| 환경 | host 한 대, Docker container, tc netem으로 링크의 지연과 손실 |
| 지표 | 서명 지연, handshake 시간(중앙값과 p99) |
| QUIC 서버 | quic-go, aioquic, quiche, s2n-quic |
| 서명 방식 | FROST, threshold RSA, threshold ECDSA |
| 네트워크·부하 | 왕복 지연, 손실률, 동시 handshake 수, 도착률 |
| 분산 구성 | signer 배치 5가지, t = 2, 3, 4, 선택 정책 |

대본:

> 실험 환경은 host 한 대 위에 container로 구성했습니다. client, QUIC 서버, signer 5대를 각각 container로 띄우고, Linux의 tc netem으로 링크마다 지연과 손실을 넣었습니다.
>
> 지표는 두 가지입니다. 서버가 서명을 요청해서 받을 때까지의 서명 지연과, client가 잰 handshake 시간입니다.
>
> 바꾼 변인은 QUIC 서버 구현체 4종, 서명 방식 3종, 네트워크의 지연과 손실률, 동시에 들어오는 handshake 수, 그리고 signer의 배치와 선택 정책입니다.
>
> 원칙을 하나 두었습니다. 측정하기 전에 예측과 판정 기준을 먼저 기록하고, 결과가 예측과 다르면 틀렸다고 그대로 적었습니다.

## 6. 실험 과정 (0:50)

슬라이드: 세 단계와 반복 측정을 화살표로.

1. 지연 주입: 실제 서명 대신 정해진 시간만큼 대기
2. 실제 signer: 서명 지연의 분해
3. 배치와 정책: 264개 조건, 지연 모델과 비교
4. 반복 측정과 새 배치 검증

대본:

> 실험은 세 단계로 진행했습니다.
>
> 1단계에서는 실제 서명 대신 정해진 시간만큼 기다리게 해서, 구현체가 서명을 기다리는 동안 어떻게 동작하는지만 따로 봤습니다.
>
> 2단계에서는 실제 threshold signer를 붙여서, 서명 지연이 무엇으로 이루어지는지 나누어 쟀습니다.
>
> 3단계에서는 signer 5대를 3개 지역에 두는 배치 다섯 가지와 선택 정책을 조합한 264개 조건을 측정하고, 지연을 예측하는 모델과 비교했습니다.
>
> 꼬리 지연은 한 번 잰 값으로는 믿기 어렵습니다. 그래서 주요 조건은 5회씩 반복해서 쟀고, 모델은 처음에 쓰지 않은 새 배치에서 다시 검증했습니다.

조건: 3단계의 조건마다 서명 1,000개를 하나씩 요청했다. 반복 측정은 199개 조건이고 실패한 실행은 없었다.

## 7. 실험 결과 (3:30)

### 7.1 서명 지연은 그대로 더해진다 (0:30)

슬라이드: `paper/figures/additivity.png`. 제목은 "handshake 시간 = 원래 시간 + 서명 지연".

대본:

> 첫째, handshake를 하나씩 맺고 손실이 없으면 handshake 시간은 서명 지연만큼만 늘었습니다. 구현체 4종의 126개 조건 모두에서 중앙값의 오차가 1 ms 이내였습니다. 서명을 기다린다는 이유로 붙는 추가 비용은 없었습니다.

조건: 주입한 지연 1~1,200 ms, client와 서버 사이 왕복 지연 1, 20, 100 ms, client 구현체 2종. 중앙값 기준이다.

### 7.2 구현체 차이는 부하와 손실에서 나타난다 (0:50)

슬라이드: `paper/figures/concurrency.png`와 `paper/figures/clientloss.png`.

대본:

> 둘째, 구현체의 차이는 두 경우에 나타났습니다.
>
> handshake 100개가 동시에 몰리면, event loop 하나에서 서명을 기다리는 aioquic은 다른 연결까지 함께 멈춰서 handshake 시간이 약 3.2초였습니다. 나머지 세 구현체는 약 73 ms로, 40배가 넘는 차이입니다.
>
> 또 client 쪽 링크에 손실이 있으면, 손실을 겪은 handshake가 구현체에 따라 약 60 ms, 200 ms, 1초씩 더 걸렸습니다. 이 크기는 서명 지연이 아니라 구현체의 손실 복구 동작에 따라 정해졌습니다.

조건: 동시 측정은 주입한 지연 50 ms, 왕복 지연 20 ms, 중앙값(aioquic 3,228 ms, 나머지 72.3~74.4 ms)이다. 손실 측정은 client 링크 손실률 2%, 왕복 지연 20 ms, 조건당 handshake 2,000회다. 150 ms 넘게 늦어진 비율은 quic-go 1.70~2.45%(약 200 ms), s2n-quic 1.80~2.50%(약 1초), quiche 0.25~0.40%다. 약 60 ms는 client가 RTT 표본을 얻은 뒤에 손실이 복구된 경우이며 주로 quiche와 aioquic에서 나타났다.

### 7.3 서명 방식별 서명 지연 (0:30, 생략 가능)

슬라이드: 표 하나.

| 서명 방식 | 서명 지연(signer 왕복 5 ms) | signer 한 대의 처리율 |
| --- | --- | --- |
| FROST(사전 계산) | 5.5 ms | 초당 1,600개 이상 |
| threshold RSA | 10.3~12.2 ms | 초당 약 200개 |
| threshold ECDSA(GG20, 사전 계산) | 41.0 ms | 초당 2~4개(계산값) |

대본:

> (생략 가능) 셋째, 서명 지연의 중앙값은 t번째로 가까운 signer까지의 왕복 시간에 계산 시간을 더한 값이었습니다. FROST는 계산이 0.3 ms 이하여서 왕복 시간과 거의 같았고, threshold RSA는 약 5 ms가 더 걸렸습니다. threshold ECDSA는 저희가 쓴 구현에서 처리율이 초당 2~4개로 계산되어 구성 비교에서 뺐습니다.

조건: 서명 지연은 (3, 5) 구성, 손실 없음. 처리율은 (2, 3) 구성에서 signer에 CPU 1개를 주고 잰 값이다. threshold ECDSA의 처리율은 presignature를 채우는 시간으로 계산한 값이며 직접 잰 값이 아니다. 쓴 library는 갱신이 멈춘 GG20 구현이다.

### 7.4 배치와 선택 정책이 꼬리 지연을 정한다 (1:40)

슬라이드 1: `paper/figures/policies.png`와 아래 표.

| 정책(t = 3, 배치 2-2-1) | 서명 지연 p99 | handshake 시간 p99 | 서명당 부분 서명 계산 |
| --- | --- | --- | --- |
| 가까운 3대만 | 70.7 ms | 91.3 ms | 3개 |
| hedge, 4대 | 28.6 ms | 55.5 ms | 12개 |
| hedge, 5대 | 26.5 ms | 57.1 ms | 30개 |

슬라이드 2: `paper/figures/events.png`. 제목은 "signer 한 대가 멈추면".

대본:

> 넷째가 핵심 결과입니다.
>
> 두 보안 조건을 모두 만족하는 구성은 t가 3이고, signer를 가까운 두 지역에 2대씩, 먼 지역에 1대 두는 배치였습니다. 이 구성에서 signer 링크에 2% 손실을 주고 정책을 비교했습니다.
>
> 가장 가까운 3대에만 요청하면 서명 지연의 p99가 70.7 ms였습니다. 3대 가운데 하나라도 패킷을 잃으면 복구를 기다려야 하기 때문입니다.
>
> 여유 signer까지 5대 모두에 요청하는 hedge 정책에서는 26.5 ms로, 62% 줄었습니다. 대가는 계산량입니다. 서명 하나에 signer들이 계산하는 부분 서명이 3개에서 30개로 늘었습니다. 4대에만 요청하면 12개로 28.6 ms였습니다.
>
> 실제 handshake 시간으로 재도 p99가 91 ms에서 56 ms 안팎으로 줄었습니다.
>
> 장애에서도 차이가 났습니다. 별도의 실험에서 signer 한 대를 강제로 종료하자, 가까운 3대만 쓰는 정책은 이후의 handshake 500개가 전부 실패했고 hedge 정책은 전부 성공했습니다.
>
> 반면 t를 4로 올리면 여유 signer가 가장 먼 지역에만 남아서, 어느 정책으로도 p99가 78 ms 근처에서 더 내려가지 않았습니다.
>
> (생략 가능) 지연 모델은 새 배치의 여섯 경우 모두에서 실제로 가장 좋았던 정책을 1순위 후보에 넣었습니다. 다만 저희가 세운 간단한 규칙은 여섯 가운데 넷만 맞아서, 미리 정한 기준에 못 미쳤습니다.

조건:

- signer 5대의 왕복 지연은 5, 5, 20, 20, 80 ms다. 서명 1,000개씩 5회 반복한 p99의 평균이며 95% 신뢰구간은 가까운 3대 ± 2.0 ms, hedge 4대 ± 6.9 ms, hedge 5대 ± 0.1 ms다. hedge 4대는 회차에 따라 25.5~38.5 ms였다.
- handshake 시간은 quic-go 서버, client 왕복 지연 20 ms, 1,000회씩 5회의 값이다. hedge 4대와 5대는 신뢰구간이 겹쳐 순위를 말할 수 없다. hedge 5대는 host에 다른 부하가 있던 때에 쟀다.
- 장애 실험은 배치가 다르다. signer의 왕복 지연이 50, 5, 100, 1, 20 ms이고, 초당 20개씩 40초 동안 handshake를 시작하면서 15초에 signer 한 대를 종료했다. 가까운 3대만 쓰는 정책이 실패한 것은 응답이 끊긴 signer를 선택에서 빼는 기능을 구현하지 않았기 때문이다.
- t = 4에서 정책 네 가지의 p99는 78.0~88.5 ms이고 신뢰구간이 서로 겹친다.
- 모델의 여섯 경우 가운데 둘은 1순위 후보가 정책의 절반을 넘어 판별력이 낮다. 규칙은 "가장 낮은 p99는 여유 signer의 위치가 정한다"는 것이고 기준은 여섯 가운데 다섯이었다.

## 8. 결론 (1:00)

슬라이드: 결론 세 줄과 한계 두 줄.

1. 키를 나누어도 handshake는 서명 지연만큼만 느려진다.
2. 꼬리 지연은 여유 signer의 위치와 그것을 함께 쓰는 정책이 정한다.
3. signer 5대, 3개 지역: t = 3, 배치 2-2-1, hedge. 계산량 10배로 p99 62% 감소.

한계: host 한 대의 emulation이다. signer 수를 늘리는 확장 실험은 하지 않았다.

대본:

> 결론입니다.
>
> 인증서 키를 threshold signature로 나누어도 handshake는 서명 지연만큼만 느려졌습니다.
>
> 서명 지연의 중앙값은 t번째로 가까운 signer의 위치가 정했고, 꼬리 지연은 여유 signer의 위치와 그것을 함께 쓰는 정책이 정했습니다.
>
> signer 5대와 3개 지역이라는 조건에서는, t가 3인 2-2-1 배치에 hedge 정책을 쓰는 구성이 보안 조건을 지키면서 꼬리 지연이 가장 낮았습니다. 계산량을 10배 쓰는 대신 p99를 62% 줄였습니다.
>
> 한계도 있습니다. 모든 측정은 host 한 대에서 지연과 손실을 emulation한 결과여서 실제 광역망에서는 수치가 달라질 수 있습니다. signer 수를 늘려 처리량을 키우는 확장 실험은 하지 않았습니다.
>
> 이상입니다. 감사합니다.
