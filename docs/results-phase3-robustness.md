# Phase 3 결과: 연결 수의 범위, signer 장애, jitter

측정일은 2026년 11월 18일이다. 용어와 기호는 [problem-definition.md](problem-definition.md) 2절, 실험 설계는 [experiment-design.md](experiment-design.md)를 따른다. 측정 전의 예측은 [worklog.md](worklog.md)의 "batch 1의 예측"에 있다. 원자료는 `results/2026-11-18-quic-conns`, `results/2026-11-18-signer-events`, `results/2026-11-18-jitter`에 있다.

## 1. 배경과 방법

[results-phase3-signer-transport.md](results-phase3-signer-transport.md)는 coordinator와 signer 사이 transport의 기본 구성을 "signer당 유지되는 QUIC 연결 4개"로 정하면서 세 가지를 남겼다. 연결 수가 동시 요청 수와 RTT_s에 따라 얼마나 필요한지, signer가 응답하지 않거나 느려질 때 정책들이 어떻게 되는지, RTT_s가 흔들릴 때 결과가 유지되는지다. 이 문서는 그 세 가지를 측정한다.

공통 조건은 다음과 같다. 서버는 quic-go이고 인증서 key는 coordinator다. RTT_c는 20 ms다. 따로 적지 않으면 signer 5개의 RTT_s는 signer 번호 순서대로 50, 5, 100, 1, 20 ms이고 scheme은 precomputation을 쓰는 FROST (3, 5)다. 이 배치에서 fastest가 고르는 signer는 RTT_s가 1, 5, 20 ms인 셋이고, fixed가 고르는 signer는 번호가 앞선 셋(50, 5, 100 ms)이다. 측정 중 host의 1분 load average는 1.5~5.0이었다.

## 2. 요약

1. QUIC 연결 4개는 측정한 모든 조건에서 loss가 T_hs 중앙값에 더하는 지연을 없앴다. 조건은 동시 handshake 30, 100, 300개, loss 1, 2, 5%, 그리고 signer의 RTT_s가 모두 50 ms인 배치다. 필요한 연결 수를 window와 packet 수로 계산한 예측은 실제보다 2~3배 많았다.
2. signer 하나가 응답하지 않으면 fixed와 fastest의 handshake는 모두 실패했다. fastest는 응답 없는 signer를 계속 골랐다. hedge와 first는 전부 성공했고 T_hs는 다음으로 가까운 signer의 RTT_s만큼 늘었다.
3. hedge 예산은 장애를 실패로 바꿨다. 넓히는 비율을 0.2로 묶은 지연 hedge는 signer가 응답을 멈춘 뒤 handshake의 21%만 성공했다. 예산이 없는 지연 hedge는 전부 성공했다.
4. signer의 RTT_s가 5 ms에서 200 ms로 바뀌면 fastest는 10초 동안 느린 signer를 계속 썼고, 그 뒤에는 그 signer를 다시 고르지 않았다. 느려진 signer가 회복해도 알 수 없는 구조다.
5. 연결이 끊긴 것을 알아채는 시간은 transport에 따라 달랐다. signer process가 죽으면 TCP에서는 handshake가 5초 뒤에, QUIC에서는 15초 뒤에 실패했다. 두 값 모두 측정 도구가 정한 제한 시간이다.
6. RTT_s에 jitter를 주면 D_sign 중앙값은 그대로였고 p95가 가장 먼 signer의 jitter 표준편차의 약 1.6배만큼 늘었다.

## 3. QUIC 연결 수

client가 handshake를 정해진 수만큼 같은 시각에 시작하는 것을 50회 반복했다. 정책은 fastest이고 nudge는 쓰지 않았다. 모든 조건에서 handshake가 전부 성공했다. 각 칸은 T_hs의 중앙값 / p95 / p99(ms)다.

### 3.1 동시 handshake 수

| --- | --- | --- | --- | --- | --- | --- |
| 30 | 0% | 43.3 / 48.1 / 49.6 | 43.4 / 48.2 / 50.0 | 43.3 / 48.3 / 49.5 | 43.9 / 49.7 / 53.9 | 43.2 / 47.8 / 49.4 |
| 30 | 2% | 43.3 / 63.0 / 66.2 | 43.4 / 50.5 / 66.5 | 43.3 / 61.3 / 72.3 | 43.4 / 49.8 / 68.1 | 43.3 / 49.0 / 68.9 |
| 100 | 0% | 48.5 / 56.8 / 60.2 | 49.4 / 58.7 / 63.4 | 49.2 / 56.9 / 59.8 | 49.3 / 57.7 / 60.7 | 49.7 / 59.1 / 63.7 |
| 100 | 2% | 61.9 / 102.1 / 119.8 | 49.6 / 69.0 / 81.8 | 49.1 / 65.6 / 79.0 | 49.4 / 62.4 / 73.1 | 49.0 / 61.7 / 76.6 |
| 300 | 0% | 78.5 / 118.4 / 130.2 | 76.0 / 109.8 / 117.0 | 76.6 / 115.4 / 142.9 | 75.5 / 106.0 / 114.4 | 82.4 / 116.4 / 126.3 |
| 300 | 2% | 127.6 / 218.7 / 298.4 | 90.2 / 156.5 / 233.5 | 84.8 / 135.7 / 164.2 | 77.1 / 116.8 / 133.9 | 76.9 / 113.3 / 126.0 |

동시 30개에서는 연결 하나로도 중앙값이 loss가 없을 때와 같았다. 100개에서는 연결 2개, 300개에서는 연결 4개에서 중앙값이 loss가 없을 때의 범위로 돌아왔다. 300개에서는 loss가 없을 때의 중앙값 자체가 75.5~82.4 ms로 100개일 때보다 26~34 ms 길다. D_sign 중앙값도 23.6~24.3 ms에서 42.1~46.3 ms로 늘었다. 동시 요청이 늘어 signer의 계산 대기와 front server의 처리 대기가 함께 는 것이며 loss와는 무관하다.

loss 5%에서는 연결 2개와 3개로 부족했고 4개에서 중앙값이 49.9 ms가 됐다. 꼬리는 loss율과 함께 늘었다. 연결 4개의 p99는 loss 0, 1, 2, 5%에서 60.7, 71.5, 73.1, 98.8 ms다.

### 3.3 signer가 모두 멀 때

signer 5개의 RTT_s를 모두 50 ms로 두고 동시 handshake 100개를 측정했다.

| loss | 연결 1개 | 2개 | 4개 | 8개 | 16개 |
| --- | --- | --- | --- | --- | --- |
| 0% | 88.7 / 101.0 / 107.3 | 89.0 / 98.9 / 102.5 | 85.0 / 95.4 / 99.5 | 84.2 / 93.2 / 95.9 | 85.3 / 98.2 / 106.4 |
| 2% | 131.3 / 234.6 / 277.6 | 119.9 / 174.0 / 189.4 | 85.4 / 133.7 / 173.0 | 90.5 / 137.2 / 167.0 | 85.8 / 139.3 / 177.4 |

연결 하나일 때 loss 2%가 중앙값에 더한 지연은 42.6 ms로, RTT_s가 20 ms일 때의 13.4 ms보다 3.2배 컸다. 전송을 기다리는 시간이 ACK가 돌아오는 주기인 RTT_s에 비례한다는 설명과 맞는다. 연결 4개에서는 이 지연이 0.4 ms였다. 꼬리는 연결을 늘려도 줄지 않았다. p99는 연결 4, 8, 16개에서 173.0, 167.0, 177.4 ms다. 이 값은 손실된 packet을 probe timeout으로 복구하는 시간(2 × 50 + 27 = 127 ms)에 처리 대기가 더해진 크기다.

### 3.4 예측과의 비교

측정 전에 연결 하나에 실리는 packet 수가 congestion window 이하가 되는 연결 수를 계산했다. 이전 측정에서 loss 2%일 때 window가 약 12 packet이었고 요청 100개가 packet 약 52개에 실렸다는 값을 썼다.

| 조건 | 예측한 연결 수 | 중앙값이 돌아온 연결 수 |
| --- | --- | --- |
| 동시 30개, loss 2% | 2 | 1 |
| 동시 100개, loss 1% | 3 | 2 |
| 동시 100개, loss 2% | 4~5 | 2 |
| 동시 100개, loss 5% | 8 | 4 |
| 동시 300개, loss 2% | 13 (8개로는 부족) | 4 |

방향은 맞았고 수는 2~3배 많았다. 계산은 요청이 한 순간에 몰린다고 가정했는데, 이전 qlog에서 wave 하나의 요청은 약 12 ms에 걸쳐 시작됐다. 그사이 가까운 signer의 ACK가 돌아와 window가 다시 열린다. RTT_s가 모두 50 ms인 배치에서 연결 2개가 부족했던 것도 같은 이유로 설명된다. 이 설명을 qlog로 다시 확인하지는 않았다.

## 4. signer 하나가 응답하지 않거나 느려질 때

client가 초당 20개의 rate로 handshake를 40초 동안 시작했다. handshake의 시작 시각은 앞선 handshake의 완료와 무관하다. 15초가 지난 시점에 signer 2(RTT_s 5 ms)에 사건을 일으켰다. 이 signer는 fixed와 fastest가 고르는 집합에 모두 들어 있다. 사건은 세 가지다.

- 죽임: signer process를 강제로 종료한다.
- 멈춤: signer container를 정지시킨다. 연결은 남아 있고 응답만 없다.
- 느려짐: signer의 RTT_s를 5 ms에서 200 ms로 바꾼다.

signer 연결은 QUIC 4개와 TCP 16개 두 가지로 측정했다. threshold RSA (3, 5)의 fastest와 first도 함께 측정했다. 사건 뒤의 handshake는 조건마다 500개다.

### 4.1 죽임과 멈춤

| 정책 | 사건 전 T_hs 중앙값 | 사건 뒤 성공한 handshake | 사건 뒤 T_hs 중앙값 |
| --- | --- | --- | --- |
| fixed | 121.2 ms | 0 / 500 | - |
| fastest | 41.2 ms | 0 / 500 | - |
| fastest + nudge 1.5 | 41.2 ms | 0 / 500 | - |
| hedge (모든 조합을 처음부터) | 42.5 ms | 500 / 500 | 71.8 ms |
| 지연 hedge 1.5 | 41.2 ms | 500 / 500 | 104.4 ms |
| 지연 hedge 1.5, 폭 4, 예산 0.2 | 41.3 ms | 105 / 500 | 104.1 ms |
| threshold RSA, fastest | 44.7 ms | 0 / 500 | - |
| threshold RSA, first | 47.9 ms | 500 / 500 | 77.9 ms |

위 값은 QUIC 연결에서 signer를 죽인 조건의 것이다. 멈춤 조건과 TCP 연결에서도 성공한 수와 T_hs 중앙값은 같았다. 예산을 둔 지연 hedge가 성공한 수는 조건에 따라 105~106개였다. 달라진 것은 실패한 handshake가 실패를 알기까지의 시간이다.

| signer 연결 | 죽임 | 멈춤 |
| --- | --- | --- |
| QUIC × 4 | 15.0초 | 15.0초 |
| TCP × 16 | 5.0초 | 15.0초 |

- fixed와 fastest는 고른 signer 셋의 응답을 모두 기다리므로 하나가 응답하지 않으면 서명을 만들지 못한다. fastest는 signer의 RTT를 응답이 올 때만 고쳐 잡는다. 응답 없는 signer의 추정값은 5 ms로 남고, fastest는 그 signer를 계속 골랐다.
- hedge와 first는 남은 signer 넷 가운데 셋으로 서명을 만든다. 세 번째로 가까운 signer가 20 ms에서 50 ms로 바뀌어 T_hs가 약 30 ms 늘었다.
- 지연 hedge는 가까운 셋이 지연 시간(32 ms) 안에 끝나지 않을 때 넓힌다. 사건 뒤에는 모든 서명이 넓혀야 하므로 T_hs가 지연 시간과 50 ms를 더한 만큼 늘었다.
- 예산은 넓히는 서명의 비율을 0.2로 제한한다. 사건 뒤에는 서명의 21%만 넓힐 수 있었고 나머지는 응답 없는 signer를 기다리다 실패했다.
- TCP에서 signer process가 죽으면 연결이 닫히므로 coordinator가 곧바로 알고 다시 연결을 시도한다. 그 시도가 연결 제한 시간 5초 뒤에 실패한다. QUIC에서는 죽은 process가 아무것도 보내지 않으므로 coordinator가 서명 제한 시간 15초까지 기다린다. 멈춤 조건에서는 두 transport 모두 15초다. 5초와 15초는 측정 도구의 상수다.

### 4.2 느려짐

각 칸은 사건 뒤 handshake의 T_hs 중앙값(ms)이다. 모든 조건에서 handshake가 전부 성공했다. QUIC 연결의 값이며 TCP 연결의 값은 1 ms 안에서 같았다.

| 정책 | 사건 전 | 사건 뒤 0~5초 | 5~10초 | 10초 이후 |
| --- | --- | --- | --- | --- |
| fixed | 121.3 | 221.3 | 221.2 | 221.2 |
| fastest | 41.2 | 221.2 | 221.1 | 71.2 |
| fastest + nudge 1.5 | 41.2 | 221.2 | 221.1 | 71.2 |
| hedge | 42.5 | 72.4 | 72.5 | 72.5 |
| 지연 hedge 1.5 | 41.3 | 105.0 | 104.9 | 71.3 |
| 지연 hedge 1.5, 폭 4, 예산 0.2 | 41.3 | 221.1 | 221.0 | 71.3 |
| threshold RSA, fastest | 44.7 | 226.0 | 225.9 | 77.8 |
| threshold RSA, first | 47.9 | 77.9 | 77.9 | 77.9 |

- fastest는 10초 동안 느려진 signer를 계속 썼다. RTT 추정이 5초 길이의 시간 창 두 개에서 가장 작은 값을 쓰기 때문에, 느려지기 전의 표본이 두 창에서 모두 빠질 때까지 10초가 걸린다. 그 뒤에는 RTT_s가 1, 20, 50 ms인 signer를 골라 T_hs가 71.2 ms가 됐다.
- 한 번 빠진 signer는 표본이 더 생기지 않으므로 추정값이 200 ms로 남는다. 그 signer가 다시 빨라져도 fastest는 알 수 없다. 이 측정에서는 회복을 시험하지 않았다.
- hedge와 first는 사건 직후부터 72.4~77.9 ms였다. 느려진 signer를 기다리지 않는다.
- 지연 hedge는 10초 동안 서명마다 지연 시간을 기다린 뒤 넓혔다(105.0 ms). 예산을 두면 넓히지 못한 서명이 느려진 signer를 기다려 중앙값이 221.1 ms였다.

## 5. RTT_s의 jitter

signer link의 지연에 정규분포 jitter를 주었다. 표준편차는 각 signer의 RTT_s의 10%와 30%다. 서명을 하나씩 요청했고 조건마다 1,000회다. D_sign 열은 중앙값 / p95 / p99(ms)다. loss는 주지 않았다.

| scheme | signer 연결 | jitter 없음 | jitter 10% | jitter 30% |
| --- | --- | --- | --- | --- |
| precomputation FROST (3, 5) | QUIC × 4 | 20.39 / 20.59 / 21.47 | 20.52 / 23.95 / 25.47 | 21.07 / 30.69 / 33.88 |
| precomputation FROST (3, 5) | TCP × 16 | 20.36 / 20.71 / 23.36 | 20.47 / 23.66 / 25.43 | 20.09 / 30.29 / 34.49 |
| threshold RSA (3, 5) | QUIC × 4 | 23.93 / 24.36 / 24.87 | 23.92 / 27.43 / 28.95 | 24.10 / 33.53 / 37.34 |
| threshold RSA (3, 5) | TCP × 16 | 24.00 / 24.38 / 24.89 | 24.09 / 27.28 / 28.51 | 24.10 / 34.10 / 37.36 |

중앙값은 0.7 ms 안에서 유지됐다. p95는 jitter 10%에서 2.9~3.4 ms, 30%에서 9.2~10.1 ms 늘었다. 가장 먼 signer(20 ms)의 jitter 표준편차는 2 ms와 6 ms이므로 p95의 증가는 표준편차의 약 1.6배다. 두 transport의 차이는 없었다.

nudge를 켠 조건의 D_sign은 켜지 않은 조건과 1.1 ms 안에서 같았다. 다만 jitter 30%에서 nudge가 서명의 95~100%에서 발동했다. nudge의 지연 시간은 최근 RTT 표본의 최솟값에 1.5를 곱해 정하는데, jitter가 크면 최솟값이 평소의 응답 시간보다 훨씬 작아진다. 불필요한 ping이 서명마다 나간 셈이다. `tc netem`의 jitter는 packet 순서를 바꾸므로 이 결과에는 순서 뒤바뀜의 영향이 함께 들어 있다.

hedge 예산이 장애 때 성공률을 21%로 떨어뜨린 것은 예측에 없었다.

## 7. 한계

- 연결 수의 측정은 scheme 하나(precomputation FROST (3, 5)), 정책 하나(fastest), signer 배치 두 가지에서 했다. 3.4절의 설명은 qlog로 확인하지 않았다.
- 장애 측정에서 사건은 signer 하나, 시점 하나, rate 하나(초당 20개)다. signer 둘 이상의 장애, 회복, region 전체의 장애는 측정하지 않았다.
- 실패까지의 시간 5초와 15초는 coordinator의 연결 제한 시간과 서명 제한 시간이다. 이 값을 바꾸면 결과가 그만큼 바뀐다.
- signer가 응답하지 않는 것을 알아채 fastest의 선택에서 빼는 기능과, 빠진 signer를 다시 확인하는 기능은 구현하지 않았다.
- jitter는 `tc netem`의 정규분포이며 packet 순서가 바뀐다. 실제 경로의 지연 변동과 다를 수 있다. loss와 jitter를 함께 준 조건은 측정하지 않았다.
- 서버는 quic-go 하나이고, host에서 실험과 무관한 process가 CPU를 쓰고 있었다.

## 8. 설계에 주는 영향

- "signer당 QUIC 연결 4개"는 동시 handshake 300개, loss 5%, RTT_s 50 ms까지 유지한다. 그 범위를 넘는 조건은 측정하지 않았다.
- 장애를 견뎌야 하는 구성에는 fixed와 fastest를 그대로 쓸 수 없다. hedge, 지연 hedge, first 중 하나가 필요하다. 지연 hedge는 평소의 요청 수가 fastest와 같고, 장애 때에는 서명마다 지연 시간만큼 늦어진다.
- hedge 예산은 signer가 응답하지 않는 동안에는 적용하면 안 된다. 예산은 부하가 몰릴 때 commitment가 모자라는 것을 막으려고 둔 것인데([results-phase3-adaptive.md](results-phase3-adaptive.md)), 장애 때에는 같은 제한이 서명을 실패시킨다. 가까운 집합이 연달아 지연 시간을 넘기면 예산을 풀거나 그 signer를 선택에서 빼는 규칙이 필요하다.
- fastest의 RTT 추정에는 두 가지가 빠져 있다. 응답이 없는 signer를 느린 것으로 취급하는 것과, 선택에서 빠진 signer를 주기적으로 다시 재는 것이다.
- 최적화 문제의 가용성 제약 A(x, f)는 이 결과로 정책별 값이 정해진다. signer 하나가 응답하지 않을 때 fixed와 fastest는 0, hedge·지연 hedge·first는 1, 예산 0.2의 지연 hedge는 0.21이다.
